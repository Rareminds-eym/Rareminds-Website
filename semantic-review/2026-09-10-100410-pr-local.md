# Token-gated event registration and payment completion

The change moves paid-event registration and payment persistence behind Cloudflare Pages Functions and service-role-only SQL RPCs. Order amounts now come from the stored registration, and order creation requires its generated `payment_access_token` instead of a registration ID and browser-supplied amount. Payment completion updates the registration and payment ledger in one transactional database function, and the Pages/React/PostgREST contracts align on the happy path. Shipping is blocked by order-creation races, missing payment recovery paths, and unique indexes that assume cleanliness the old schema did not enforce.

Watch for: **confirmed** duplicate or orphan Razorpay orders during concurrent/retried creation; **confirmed** pending registrations becoming unpayable after token loss; **confirmed** captured payments becoming unrecoverable after transient completion failure; **confirmed** migration failure when legacy rows violate the new uniqueness assumptions.

**Verdict**: NEEDS_CHANGES

## High-level view

The registration RPC generates an unguessable UUID token for paid registrations and returns it through the Pages endpoint to both React entry points. The create-order endpoint requires that token and resolves amount and currency server-side, so **confirmed** registration ID alone no longer authorizes an order.

Order reuse begins only after a payment row exists, but Razorpay order creation happens before that insert. **Confirmed** concurrent requests or failed persistence after a successful provider call can therefore create multiple valid external orders while the database retains at most one.

Payment completion locks and updates both rows in one PL/pgSQL invocation; retries succeed only for the same order/payment pair. The SQL signatures, PostgREST parameter names, scalar results, and React JSON fields match.

Recovery stops at the browser session boundary. **Confirmed** closing or reloading loses the only pending-registration token, and **confirmed** a transient database failure after capture discards the callback’s signed payment tuple instead of retrying completion.

The migration adds unique payment indexes to a schema that previously had only ordinary indexes. **Confirmed** it performs no duplicate preflight or reconciliation, so plausible legacy duplicates abort deployment.

<details>
<summary>Details</summary>

## Razorpay order creation is not idempotent across the provider/database boundary

`create-order` reads payment context, creates a Razorpay order, and only then calls `record_event_payment_order`. The advisory lock exists only inside that final RPC and cannot cover the provider call. Two **confirmed** concurrent requests can both create orders; the first insert wins and the second fails the registration uniqueness index, leaving its provider order valid but untracked. The same **confirmed** orphan occurs when Razorpay succeeds and PostgREST fails before commit.

Atomically reserve order creation before contacting Razorpay. Retries must use provider-supported idempotency or reconcile a stable external key before issuing another order; a database uniqueness error after the external resource exists is too late.

## Pending registrations cannot resume after token loss

The registration RPC returns `payment_token` once, and both React flows keep it only in component state. Closing resets that state; reload or navigation also loses it. Another registration is **confirmed** rejected as already registered, and no endpoint can re-authorize the pending row after fresh email verification.

Add a recovery contract that returns or rotates payment authorization for the existing pending registration after a new verification proof, while retaining the server-calculated amount.

## Captured payments lose their retry tuple on transient completion failure

The verify endpoint checks Razorpay’s signed order/payment tuple before calling the completion RPC. If PostgREST transiently fails, the endpoint returns 503 and the modal stores only an error string; the tuple is **confirmed** neither retained nor retried. Clicking Pay reuses an order that may already be paid, so the idempotent `complete_event_payment` retry branch is not reachable through the client.

Retry verification with the same tuple until a definitive state response, with server-side webhook/reconciliation as the fallback when the browser disappears.

## New payment uniqueness constraints can abort on legacy rows

The baseline schema permits duplicate non-null `payments.registration_id`, `razorpay_order_id`, and `razorpay_payment_id`; it defines only non-unique indexes for registration and order IDs. The migration creates three unique indexes without checking or reconciling existing rows. This **confirmed** assumption makes any plausible duplicate history abort the migration.

Add preflight queries and deterministic reconciliation before index creation, or fail early with diagnostics identifying every conflicting row.

</details>
