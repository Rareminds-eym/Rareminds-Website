# Fail-closed email BFF and delivery-safe OTP replacement

The latest fixes retain the previously delivered OTP while a replacement is sent, add IP and hashed-recipient throttles, and route all reviewed mail through the bound worker RPC. Failed replacement delivery removes only the new row, preserving the prior code. One release blocker remains: successful delivery treats retirement of older OTPs as best-effort, so an older code can remain usable after the endpoint reports success.

Watch for: **confirmed** successful OTP resend can leave older OTP rows valid when post-delivery cleanup fails.

**Verdict**: NEEDS_CHANGES

## High-level view

OTP replacement now uses insert, deliver, then retire ordering. Failed delivery preserves the prior delivered code, but **confirmed** post-delivery retirement failure is logged and ignored, so success does not guarantee that older codes were invalidated.

Every email action consumes an IP/action bucket, while OTP send and verification also consume a bucket keyed by action plus a SHA-256-derived recipient identifier. Missing bindings, limiter exceptions, and denied limits stop the request, confirming both dimensions fail closed without exposing recipient addresses in rate-limit keys.

All outbound mail in the reviewed handlers calls `EMAIL_SERVICE.sendEmail`; the only direct `fetch` is for OTP persistence through Supabase REST. The configured binding targets the authoritative `EmailService` RPC entrypoint whose export and `sendEmail` contract were directly verified for this pass.

## Successful resend does not guarantee single-code validity

After replacement delivery succeeds, `sendOtp` deletes older unverified rows while excluding the replacement ID. The delete at `functions/api/email/[action].ts:340-349` has a `.catch(...)` that only logs failure, after which the route returns `200` and “OTP sent successfully.” This is **confirmed** to leave both codes usable after a transient Supabase failure because `verifyOtp` searches for any unexpired row matching the submitted OTP. Successful resend must not report completion while prior generations remain accepted.
