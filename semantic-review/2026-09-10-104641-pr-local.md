# Service-bound payment and email provider isolation

The change moves every reviewed secret-bearing Razorpay operation behind the Pages payment BFF and the existing payment worker RPC surface. Email-producing application paths terminate at Pages handlers that call `EMAIL_SERVICE.sendEmail`, while Supabase remains limited to persistence and transactional state changes. Legacy Supabase payment implementations, email functions, and database-triggered email transport are retired in the changed tree. No actionable blocker remains in the requested scope.

Watch for: no **confirmed** or **likely** blocker remains in the payment binding, provider transport, signature verification, email delivery, or legacy-path retirement.

**Verdict**: APPROVED

## High-level view

`PAYMENT_WORKER` binds `razorpay-api` without a named entrypoint, matching that worker's default `PaymentService` export. Order creation, checkout-result verification, and webhook verification call its `createOrder`, `verifyPaymentSignature`, and `verifyWebhookSignature` RPC methods; website-side Supabase requests only reserve, finalize, or complete payment state.

The browser loads Razorpay Checkout and forwards its signed result to the Pages BFF. It receives the public checkout key from the order response but contains no Razorpay secret, local signature implementation, or direct order API request.

Application email routes call the named `EmailService.sendEmail` RPC exposed by `shared-email-api`. Browser code calls only Pages endpoints, and Supabase HTTP use in the email BFF stores or consumes OTP state rather than delivering mail.

Supabase function declarations and source implementations for the old payment and email transports are removed or reduced to retirement markers. The migration drops database functions and the PDF trigger that previously called Supabase email endpoints; both external worker repositories are clean.

## Default `PaymentService` is the sole provider boundary

The Pages binding omits `entrypoint`, and `razorpay-api/src/index.ts` defaults to `PaymentService`. The BFF's three provider-sensitive operations map directly to methods present on that class. The only Razorpay provider URL, Basic credential construction, payment HMAC, and webhook HMAC found in executable code are inside the unchanged payment-worker repository.

Calls to `reserve_event_payment_order`, `finalize_event_payment_order`, and `complete_event_payment` establish authoritative amount and lifecycle state through PostgREST, but only `PAYMENT_WORKER.createOrder` contacts Razorpay and only worker RPC verifies either signature.

## Razorpay Checkout remains an untrusted UI client

`PaymentModal` loads `https://checkout.razorpay.com/v1/checkout.js`, opens Checkout with the worker-returned public key and order, and sends the captured order/payment/signature tuple to `/api/payments/verify-payment`. It neither decides signature validity nor marks database state complete directly; Pages does so only after worker verification.

## `EmailService.sendEmail` owns outbound delivery

The notification, OTP, PDF, and university-contact Pages handlers all invoke `env.EMAIL_SERVICE.sendEmail`. The binding names the existing `EmailService` export from `shared-email-api`; its checked repository is clean and exposes the expected typed RPC method. Executable website code contains no Supabase Function invocation or direct email-provider endpoint.

The migration's Supabase calls are persistence only: OTP storage/consumption and registration/payment transactions. It removes the legacy database functions that issued HTTP email requests and drops the PDF trigger before dropping its handler, while `supabase/config.toml` no longer enables payment or email Edge Functions.
