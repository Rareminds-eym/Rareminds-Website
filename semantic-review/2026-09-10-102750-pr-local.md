# Recoverable token-gated paid event checkout

The latest fixes put paid registration and checkout authorization behind a one-time email proof and a rotatable payment token. A database reservation now commits before Razorpay order creation, while browser retry and the signed Razorpay webhook converge on the same transactional completion function. The SQL RPCs, PostgREST payloads, and both React registration paths agree on identifiers, amounts, currencies, and states. No release-blocking local-code issue remains in the requested scope.

Watch for: no **confirmed** or **likely** release-blocking concern remains in the reviewed registration, payment, SQL, webhook, contract, or migration paths.

**Verdict**: APPROVED

## High-level view

Email proofs are single-use and bound to the normalized email. A fresh proof rotates authorization for an existing paid registration only while it remains pending, restoring checkout without making a registration ID sufficient authorization.

The registration lock establishes one payment reservation before the provider call. The committed `creating` state fails closed, concurrent callers wait, finalized reservations reuse the stored order, and one request UUID remains available in the Razorpay receipt and notes for reconciliation without changing the payment worker.

Finalize and complete validate the stored tuple and update related rows transactionally. Completion is idempotent only for the same order/payment pair and clears payment authorization after success.

The browser retains a captured signed tuple across transient confirmation failures. The webhook independently verifies Razorpay's HMAC over the raw body and sends captured or paid events through the same completion RPC.

Migration preflight checks the legacy values covered by the new partial unique indexes. The request-ID column is introduced null before its unique index, then populated only by the serialized reservation path.

## Reservation defines the provider-call boundary

`reserve_event_payment_order` locks the payable registration before inspecting or inserting its payment row, so only the caller receiving the committed request UUID contacts Razorpay. Later callers either wait on `creating` or reuse a finalized `pending` order. A provider or persistence failure intentionally leaves `creating` fail closed; the deterministic receipt and notes retain the identifier needed for operator reconciliation under the fixed-worker constraint.

## Finalize and complete preserve the captured tuple

Finalization requires the registration and request UUID that own the reservation and compares provider amount and currency with stored registration values. Completion locks the uniquely addressed payment and related registration, accepts only pending-to-completed, and treats an exact repeated order/payment pair as success; a different tuple cannot overwrite captured payment data.

## Browser retry and signed webhook share completion

`PaymentModal` stores the Razorpay callback tuple before BFF verification. Transient failures preserve it and block dismissal while exposing confirmation retry; definitive signature rejection clears it. The webhook covers browser loss by verifying `X-Razorpay-Signature` against the untouched body before extracting the tuple from supported captured events.

## Duplicate guards cover each legacy uniqueness assumption

Preflight checks normalized event/email groups and the legacy non-null payment keys made unique: registration ID, Razorpay order ID, and Razorpay payment ID. Their partial-index predicates match the checks. `order_request_id` needs no legacy scan because this migration introduces it with null values before creating its unique index.
